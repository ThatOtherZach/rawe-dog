# Authenticity + Role Matching Guardrail System

**Purpose**  
Prevent resumes and cover letters from sounding like they were generated by rewriting the job posting. Maximize evidence-based alignment, not lexical similarity.

---

## Core Principle

Always write **from Zachary’s actual experience outward** to the job requirements. Never rewrite the job posting in the first person.

**Good:**  
> "At TD Securities I coordinated monthly Salesforce releases, gathering requirements from Global Risk stakeholders and writing user stories."

**Bad:**  
> "Experienced translating business needs into actionable specifications while collaborating with cross-functional stakeholders."

The first originates from real experience. The second could have been generated solely from the job posting.

---

## Generation Pipeline (Strict Order)

1. Select sources using the Role-Type Alignment Table below.
2. Pull only relevant evidence from the chosen workplace summaries. Never dump full files.
3. Write from the evidence first — concrete projects, tools, problems, ownership, and outcomes.
4. Only after the draft is complete, check that important ATS keywords appear naturally.
5. Run the three authenticity tests before final output.

## Authenticity Rules (Non-Negotiable)

### Anti-Mirroring
Do **not** closely paraphrase these common job-posting phrases:

- translating business needs
- actionable specifications
- stakeholder alignment
- cross-functional collaboration
- roadmap planning
- business process improvements
- continuous improvement
- dynamic environment / fast-paced environment
- working software over exhaustive documentation
- delivering value
- strategic initiatives
- operational excellence
- scalable solutions

Rewrite them using what Zachary actually did.

### Allowed Technical Terms
These may be reused naturally:

- Salesforce
- Jira
- Agile / Scrum
- ERP / PLM
- SQL / APIs
- Data Loader
- Digital Product Passport
- UAT / QA
- Acceptance Criteria
- User Stories
- Flow / LWC / Apex / SOQL

### Evidence-First Rule
Every paragraph and every bullet must contain at least one concrete piece of evidence that originates from Zachary’s history:

- Company or project name
- Specific tool or method
- Metric, volume, or timeline
- Ownership or problem solved

If a paragraph only contains skills + adjectives, rewrite it.

---

## Three Mandatory Tests

Run these before returning any final document.

1. **Specificity Test**  
   “Could this paragraph describe thousands of applicants?”  
   → If yes, rewrite with concrete evidence.

2. **Job Posting Dependency Test**  
   “If the job posting disappeared, would this paragraph still make sense?”  
   → If no, rewrite so it is driven by Zachary’s experience.

3. **Lexical Similarity Check**  
   Scan for repeated employer phrasing. Reduce unnecessary overlap while keeping real technical terms.

---

## Style & Formatting Constraints

- Voice: clear, direct, thoughtful, outcome-oriented
- Never use the em-dash (—). Use commas instead.
- Resume bullets: strong action verb + concrete context + outcome
- Prefer 4–6 bullets per role
- Combine content from multiple workplaces only when it strengthens the case for a specific requirement
- Use Saym Services projects sparingly (2–3 max) and frame them as client work when possible

---

## Final Validation Checklist

- [ ] Every major claim is supported by real evidence from the source files
- [ ] Every paragraph contains candidate-specific details
- [ ] No close paraphrasing of job-posting language
- [ ] Technical terms preserved where accurate
- [ ] Corporate buzzwords minimized
- [ ] Document reads like a human describing their career, not a job posting rewritten in first person

**Success metric:** How accurately Zachary’s real experience satisfies the posting — **not** how closely the wording matches it.
